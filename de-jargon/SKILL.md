# de-jargon：清除工程黑话

## 这个 skill 解决什么

中文技术写作里有一批词，看着专业，实际不携带信息：

> 门禁、解冻、收窄、切片、收口、落地、闭环、兜底、对齐、沉淀、颗粒度、打通、卡点、水位、心智、抓手、赋能、骨架、锚点、正交、咬合

它们大多是英文隐喻被逐字直译的残留（gate / thaw / narrow / slice / converge / land / closed-loop / fallback），共同特征是：**在中文里另有一个更强的本义，读者每次遇到都要先做一次"这不是字面意思"的换算，而换算结果往往不唯一**。

危害不在难看，在**一个词盖住了好几种不同机制**。看到「启动时做权限门禁校验」，读者不知道是校签名、查 ACL、还是读配置开关。

**与 humanizer 的分界**：humanizer 把文字变口语、变自然，面向小说和公众号。本 skill 相反 —— 目标是**更精确**，把模糊的词换成具体的函数名、状态值、失败行为。不要为了"像人话"把技术文档改得随意。

## 核心判定：三条测试

不要凭感觉判定。用这三条，可复现：

1. **能否指向一个代码实体** —— 这个词能否对应到具体的函数、字段、状态值、异常、协议字段、配置项？
   「权限门禁」指不出 → 黑话。「校验客户端签名」指向 `verify_signature()` → 合格。
2. **反义词是否存在** —— 「解冻」预设了 `冻结` 状态。代码里没有这个状态机，词就是空的。
3. **删掉是否损失信息** —— 删掉后技术信息不减，它是修辞不是信息。**这一条命中率最高。**

详细成因分析、族谱、以及**一词多义的拆分表**（「兜底」可能是默认值/降级返回/备用数据源…，「对齐」可能是字段名相同/取值域相同/行为一致…）：

→ 读 `references/jargon-families.md`

**必须先拆再改。** 黑话的危险在于一个词能指五种东西，直接换同义词一定换错。

## 两种使用场景

### 场景 A：正在写（默认，预防）

生成或修改注释、文档、命名时，边写边挡。自查清单：

- [ ] 这句话里的抽象名词，能不能指向一个具体的函数/字段/状态？
- [ ] 有没有用数量词冒充严谨（"三道防线""双保险"）？
- [ ] 有没有写完动作不写对象（"处理完成""已闭环"）？
- [ ] 变量名是不是 `data` / `info` / `Manager` / `Helper` 这类泛词兜底？
- [ ] 失败路径有没有写清楚"下一步做了什么"，而不是"已兜底"？

### 场景 B：审查存量

跑扫描器，按报告处理。

```bash
python {skill_dir}/scripts/scan.py .                    # 全库
python {skill_dir}/scripts/scan.py doc/ src/            # 指定目录
python {skill_dir}/scripts/scan.py . --level A          # 只看 A 级
python {skill_dir}/scripts/scan.py . --family buzz,gate # 只看某几族
python {skill_dir}/scripts/scan.py . --json > r.json    # 机器可读
git diff --name-only | python {skill_dir}/scripts/scan.py --paths-from -   # 只查本次改动
```

`{skill_dir}` 是 Skill 工具返回的 base directory。

扫描器能区分三种位置并在报告里标出：**注释**、**字符串字面量**（`⟨在字符串里⟩`）、**标识符**（`⟨在代码里⟩`）。这个区分很重要 —— 同一个词在注释里该改，在字符串里可能只是文案，在标识符里改动成本最高。

退出码：有 A 级命中返回 1，可接 pre-commit 或 CI；`--no-fail` 关闭。

## 执行规则

分级处理，不要一把梭：

| 位置 | 怎么处理 |
|---|---|
| 代码注释 | **直接改** |
| 日志文案、错误提示 | **直接改** |
| 标识符（变量/函数/字段） | **直接改**，但改完全局搜索引用并重新构建验证 |
| `.md` / `.txt` 文档 | **只出报告**，等确认后再动。文档里的措辞往往承载过审阅决策 |
| 引用他人原话、issue、会议记录 | **只标注，不改**。改了会失真 |
| 未提交的 commit message | 直接改 |

改文档时给出**建议措辞**而不是只报位置。报告格式：`文件:行号 → 原句 → 建议`。

## 改写原则

**不是同义词替换，是还原成它想说什么。**

- ✗ 机械替换：「门禁」→「鉴权」→ 结果写成「权限鉴权校验」（更糟，两个字都废）
- ✓ 先拆后写：「启动时做权限门禁校验」→ 问是哪一种 → 「启动时校验客户端签名，失败则拒绝连接」

改写后要满足：**读者能根据这句话写出代码，或定位到具体代码。**

三条硬约束：
1. 不新增原文没有的技术断言。原文模糊就保持模糊，但把模糊说明白（"未确认"也是信息）。
2. 保留原有的确定程度。「应该」不要改成「会」。
3. 专有名词、代码标识符、错误码原样保留。

## 真术语不要动

幂等、原子性、序列化、超时、重试、退避、熔断、限流、降级、灰度、埋点、事务、竞态、背压、水位线、状态机、断点续传、归一化、数字孪生、骨架屏 —— 这些有唯一可验证的定义，是术语不是黑话。

判据：**能否对应到有明确定义、可被验证或测量的机制。**

完整的白名单、以及各类标识符改名方案（`slot` / `gate` / `thaw` / `watermark` 等）：

→ 读 `references/naming.md`

## 遇到不确定就问

不要自作主张改这四类，说明情况让用户决定：

1. **用户/团队的口头习惯** —— 有人就是习惯说「兜底」且团队都懂
2. **行业既有译名** —— 「灰度」「背压」已是通用译法，改了反而不专业
3. **业务专有名词** —— 如果「解冻」是个真实功能名（账号解冻），它是名词不是黑话
4. **拿不准是术语还是黑话** —— 直接问，并给出你的倾向和理由

## 常见错误

- **只报不改，报完就完** —— 按上表处理，该改的直接改
- **把技术文档改成口语** —— 这不是 humanizer。目标是精确，不是亲切
- **一次改太多文件** —— 文档改动按主题分批，一次一批，每批能 review
- **改标识符不重新构建** —— 改名必须验证编译通过
- **把术语当黑话删掉** —— 先过白名单，再看测试 1
